计算并核对 SHA 校验和

本工具把文本或一个本地文件转换成可重复的十六进制完整性指纹。下载页面、构建流程或数据规范写明哪一种算法，就选择对应的 SHA-256、SHA-384 或 SHA-512。计算交给浏览器的 Web Crypto 完成，输入内容不会为了计算而发送到本站。

三步完成校验

  1. 先确认算法按照校验和来源选择 SHA-256、SHA-384 或 SHA-512。比较前必须使用同一种算法；两个摘要相同本身不能证明原始输入完全相同。
  2. 输入文本或选择文件文本填写后点击“计算文本哈希”；文件则先选择，再点击“计算文件哈希”。文件上限为 32 MiB，两条输入路径互不混合。
  3. 复制或核对结果可以复制小写十六进制结果，也可以把发布方提供的值粘贴到预期值输入框中比较。匹配表示所选算法下摘要相同；预期值可信时，这是很强的完整性证据，但不是输入完全相同或发布者身份的证明。

适合使用校验和的场景

核对下载文件

软件发布页若给出 SHA-256 值，可对下载后的压缩包使用同一种算法，然后比较两个字符串。摘要相同通常是文件未被改变的有力证据，但哈希碰撞在数学上仍然可能；预期值是否可信也取决于获取渠道。

确认系统间传递的文本

对配置片段、接口示例或发布说明计算指定算法的结果。文本会先由 TextEncoder 编码成 UTF-8 字节，因此大小写、空格、换行方式和看不见的字符都会改变结果。

记录构建产物指纹

移动较小的安装包或数据文件之前记录 SHA-384 或 SHA-512，之后重新计算即可发现字节是否改变。记录时应把算法名称与结果放在一起，因为仅看一串十六进制字符不能可靠判断算法。

处理方式与边界

  • 文件路径会调用 arrayBuffer()，把整个所选文件读入内存后再交给 Web Crypto，并非分段处理。32 MiB 上限用于控制内存占用，更大的文件需要使用其他校验程序。
  • 文本路径直接使用 TextEncoder 生成的 UTF-8 字节，不会替用户统一 Unicode、空格或换行符。因此肉眼看起来相同的文本，也可能因为底层字节不同而得到不同结果。
  • 比较功能只会去除两端的首尾空白并转成小写，不会验证预期值的十六进制格式或长度。两个相同的非空字符串即使不是有效摘要，也可能显示匹配。
  • 若连续发起多个异步计算，最后一次请求的结果生效并显示在界面中。较早的任务即使稍后结束，也不会覆盖较新的输出和状态。
  • 加密哈希是完整性指纹，不是加密、身份认证或密码哈希。它不能还原输入，不能证明内容由谁创建，也不能让来自不可信渠道的校验和自动变得可信。

常见问题

应该选择哪一种 SHA 算法？

核对现有结果时，必须选择来源明确写出的同一种算法。同一份输入的 SHA-256 不会等于 SHA-384 或 SHA-512。没有外部规范时可以按自己的流程决定，但本页面不会替具体协议作安全设计选择。

为什么只改一个字符，结果就完全不同？

摘要算法本来就会让很小的字节变化产生差异很大的输出。遇到不匹配时，请检查大小写、空格、末尾换行和行尾格式；屏幕上可见的字符并不能展示全部 UTF-8 字节。

校验和匹配就代表文件安全吗？

不是。匹配表示指定算法下摘要相同，是完整性核对的证据，但无法排除碰撞，也不等于恶意内容扫描。如果攻击者可以同时替换文件和校验和，单纯比较仍无法认证来源。

计算过程会上传或保存内容吗？

计算在当前浏览器中通过 Web Crypto 执行。本工具不会为输入文本、所选文件或结果新增网络请求、跟踪或存储。不过，浏览器扩展和设备本身的环境并不属于页面能够控制的范围。
