Generation details and limitations

Each value starts with 16 bytes filled by crypto.getRandomValues(). Version 4 keeps random payload bits; version 7 places the current 48-bit millisecond timestamp first and retains random payload bits. Both set RFC 9562 version and variant bits. Batch size is one of 1, 10, 100 or 1000. Uppercase and hyphens affect presentation only.

The page performs no persistence and no deduplication check across the current batch, earlier batches, other tabs, or external systems. Random UUID collisions are expected to be unlikely for ordinary identification work, but the interface does not prove uniqueness. Applications that require a database uniqueness constraint must still enforce it and retry on conflict.

UUIDs are identifiers, not secrets or authentication tokens. Do not treat an unguessable-looking UUID as authorization. Copy All and Download TXT export only the current local output. Namespace-based UUID versions and ULID are not implemented.

UUID v4 and v7 FAQ

How do UUID v4 and v7 differ?

Version 4 uses random payload bits. Version 7 begins with a Unix millisecond timestamp for approximate chronological ordering and uses random bits for the remaining payload. Both use the RFC 9562 variant.

Is an uppercase or unhyphenated value a different UUID?

No. Hexadecimal letter case and hyphen placement are textual presentation. They preserve the same bits, although a receiving validator may insist on one spelling.

Does the generator guarantee every value is unique?

No absolute guarantee or registry check is made. Use a unique index or equivalent rule in the system of record when duplicate rejection is a requirement.

Can a UUID be used as a password or access token?

No. UUIDs identify objects; they do not establish permission. Authentication tokens need a threat model, suitable entropy, lifecycle controls, secure storage, and validation designed for authentication.
